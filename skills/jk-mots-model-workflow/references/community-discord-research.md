# Community Discord research: model choices and observed limits

Use these notes for character and weapon-model decisions. They cover a bounded set of saved Massassi Discord messages, with participant reports distinguished from the workflow's own file analysis. They do not establish new game-runtime results.

## Choose how much weapon-hand integration to take on

| Route | Useful when | Cost or limitation |
| --- | --- | --- |
| Keep the stock external weapon hand | Fastest playable character is the priority | A mechanical or alien character may show a mismatched hand |
| Add character-specific geometry that conceals the stock hand | One skin should improve without changing shared weapon resources | Coverage depends on the selected weapon and pose; bulk can damage the silhouette |
| Replace shared external weapon assets | The mod intentionally gives all affected characters the same treatment | Resource replacements affect other users of those assets |
| Select weapon assets with character-aware scripting | Per-character correctness matters more than a simple skin package | Requires explicit scripting, weapon-state and multiplayer integration work |

Shred's reply on 27 September 2026 identifies the shared-resource problem: replacing the external fist for an ordinary multiplayer setup changes it for other player characters using that resource. He subsequently encourages trying DarkahnKiralv's proposed larger character hand as concealment. This is a useful constraint and an experimental suggestion, not a certification that concealment works with every weapon. [Shred's limitation](https://discord.com/channels/881034839401328680/881044857328652328/1553970405952200725), [DarkahnKiralv's proposal](https://discord.com/channels/881034839401328680/881044857328652328/1554028887749562409), [Shred's follow-up, 28 September](https://discord.com/channels/881034839401328680/881044857328652328/1554079206810583071)

The counterexample matters. On 30 September, DarkahnKiralv reports acceptable concealment for most tested uses but continued exposure with the Repeater; increasing the covering hand further looked excessive. A following message describes deriving a slightly larger silver hand from the regular fist. Credit the proposal and its reported limitation together. Do not turn Shred's encouragement into a solved all-weapons recipe. [Repeater report](https://discord.com/channels/881034839401328680/881044857328652328/1554765965454086236), [construction description](https://discord.com/channels/881034839401328680/881044857328652328/1554766828335796235)

Existing project analysis supports inspecting **placement**, not merely assuming the Repeater has a larger hand shape: the studied stock resources contain different placements of substantially the same hand geometry. Static containment measurements and a participant's appearance report remain separate evidence. The [Terminator case study](terminator-case-study.md) retains the local derivation and licensing boundaries; no extracted stock hand is distributed by this reference.

The engine-source distinction is also useful: the external weapon mesh is installed on a player's weapon render object, while POV model and animation operations use a separate first-person object. A character body's hand, an attached external weapon hand and first-person hands therefore need separate decisions and tests. The source corroborates the architecture, not every reported original-engine visual result. [Pinned weapon/POV functions](https://github.com/shinyquagsire23/OpenJKDF2/blob/0dbd1ea8bb2211c158f6af928b5e4fb14dfa0dac/src/Cog/jkCog.c#L206), [weapon attachment drawing](https://github.com/shinyquagsire23/OpenJKDF2/blob/0dbd1ea8bb2211c158f6af928b5e4fb14dfa0dac/src/World/jkPlayer.c#L984)

For an ordinary multiplayer skin, start with the stock-hand or modest-concealment option and disclose the remaining seam. If the user wants full coverage, make character-aware weapon integration an explicit second phase. Check each carried weapon, alternate/empty state, mounting, aiming, firing, respawn and a connected player's view. This test plan is our synthesis; the saved messages do not show that entire matrix being completed.

## Use authoring tools and diagnostic textures deliberately

Stormtrooper recommends Blender-Sith for model design and animation in the 26 September discussion. LadyEebs separately states that Blender was used to make the Redux models. Those are useful community endorsements and authorship testimony. Neither message establishes support for every Blender release, all native export fields or a newly completed automation workflow. Choose a documented add-on version and follow the [tested export and baking methods](blender-export-and-baking.md). [Stormtrooper](https://discord.com/channels/881034839401328680/881044857328652328/1553580220588752937), [LadyEebs](https://discord.com/channels/881034839401328680/881044857328652328/1553584207396208751)

Cogking describes a diagnostic loader mode that substituted a 128-square image with an orientation letter and graduations. The transferable method is to temporarily use an asymmetric, numbered calibration image to reveal UV orientation and scale. Keep it distinct from a finished material and compare the result at each conversion step. The captured parent reply is unavailable, so no particular failure or successful repair is inferred. [Cogking, 29 September 2026](https://discord.com/channels/881034839401328680/881044857328652328/1554623377451389014)

## Reading lessons and exact coverage

Quoted replies must remain separate from the reply author's own words. In the retained capture of Shred's first hand response, a convenience `body` field contains DarkahnKiralv's quoted question, while the complete `text` contains Shred's actual answer beneath his name and timestamp. A second response has the same problem. Some quoted edit timestamps also contaminate convenience time fields. Attribution here uses each selected message's own full-text header and content; display dates are retained without inventing their timezone.

The [source ledger](evidence/community-discord-sources.json) describes **300 unique messages across three captured channels**: editing (210), showcase (57) and massassi (33). They occupy 12 observed result-page numbers. Twenty-five saved page records contain 15 nonempty captures, 10 empty captures and 75 duplicate message occurrences. The retained visible headers span 26–30 September 2026. Broader search date bounds do not mean the complete month, older history or the entire server was read.

All three channels' available message text was screened with broad model/material/animation terms; relevant full texts and their surrounding captured replies were checked. General conversation and level-design discussion were excluded from the model methods. Images, attachments and linked downloads were not inspected for this reference. No Discord UI interaction, new fetch, game launch or connected multiplayer test occurred during this saved-capture analysis. Message links may require Discord membership and were not freshly opened. Public files contain concise original technical synthesis and attribution, not full chat transcripts, signed attachment URLs or private filesystem paths.
